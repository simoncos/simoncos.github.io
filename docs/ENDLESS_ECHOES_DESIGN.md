# 漫无止尽的回响：设计思路与维护指引

整理日期：2026-10-03；2026-10-04 按已发布的改版（`e752a7b`）和其后的音频批次（路径和弦曲、终章、重配和弦）刷新。依据会话中作者的要求、确认和修订，以及代码、数据、素材与 QA 记录。

**核心方向：从一首歌的记忆出发，沿歌词与意象的关联，走入一个可以分岔、重逢、回到起点的音乐空间。** 这是对整个会话的归纳，不是作者的逐字原话。

本指引保留设计意图，供以后改版、扩展和新建谜题使用。作者明确提出的要求、本文归纳的原则、当前实现参数与尚待验收的部分分别说明。文中不再附歌曲、路径和和弦的完整表：它们很快会过时，实际编辑以 [`data/music-riddle.json`](../data/music-riddle.json) 为唯一歌曲数据源，字段约定见[数据约定](MUSIC_RIDDLE_DATA.md)。

## 1. 作品定位与体验目标

《回响》是从 2017 年虾米广域音乐谜题复原并扩展而来的交互作品。在网站中归入 **Work → Games / 作品 → 游戏**，首页属于「创造」。作者先纠正了「放在音乐」的分类，再要求建立游戏分类；旧「项目」分类改为「工具」。现有 `/gallery/music/` 地址是历史路径，不代表作品仍归入音乐分类。

基本动作是「读线索 → 猜下一首歌 → 接上一条路」。歌曲之间的关联、探索顺序和个人走过的路径共同构成作品。完整网络提供方向感，单首歌的文字、花朵与和声提供停留的理由。

从会话可归纳出五条优先原则：

| 原则 | 对设计的具体约束 |
| --- | --- |
| 关联比顺序重要 | 允许多条出路、汇合、回环和死胡同；不能把作品压成按编号播放的歌单。 |
| 先读懂，再感受 | 路径、箭头、文字和操作必须清晰，构图与装饰围绕这些任务组织。 |
| 视觉、文字、声音各司其职 | 花朵承载视觉情绪，和弦回应节点，文案直接说明猜歌、提示和探索。 |
| 允许自由抵达 | 到达终点与全收集是两种完成程度；玩家可以先抵达，再回来探索。 |
| 保留修改能力 | 统一数据、稳定 ID、证据与作者确认分开记录，扩展后继续保留旧进度。 |

当前规模是 **26 首原存档歌曲 + 10 个新增常规节点 = 36 个常规节点、47 条有向路径，另有 1 个隐藏尾声**。进度显示 `36/36`；隐藏尾声是全收集后的额外回响。

## 2. 复原与扩展的证据边界

### 2.1 先确定歌曲身份和来路，再解释谜面

最初可用的材料是 Obsidian 中的原作记录、[豆列](https://www.douban.com/doulist/45894638/)和[2017 年原始介绍](https://www.jianshu.com/p/bacb95af08b1)。失效的虾米链接带来两种不同问题：某个条目到底是哪首歌，以及条目之间的箭头朝哪里走。仅凭谜面「很像某首歌」不能同时解决这两个问题。

作者后来提供了自己的虾米收藏导出（CSV，保存在仓库之外）。其中目标歌单的 26 段推荐语，去除空白后与豆列 26 条评论逐条唯一匹配，补足了歌名与条目的身份对应。这份存档支持原有 31 条歌名层面的路径，但不穷尽未收录的死胡同，也不能证明不同旧地址对应同一个录音版本。

读取此类 CSV 时，歌单名只在分组首行出现，需要向后继承；直接筛选含「回响」的行会漏掉后续歌曲。私人收藏全集不应为了复原一个作品而全部进入公开仓库。

### 2.2 最容易重犯的方向错误

原推荐语的上半部「上一首」记录的是**进入当前歌曲的来路**，下半部才是当前歌指向下一首的谜面。豆列编号是条目索引，不是游戏顺序。

本次争议最终厘清的关系是：

```text
倒带人生 → 今天等我来 ─┐
                      ├→ 任我行 → 浮夸 → 孤独患者
           幸福摩天轮 ─┘
```

第 15 条《任我行》中的《幸福摩天轮》和《今天等我来》是来路。因此《倒带人生 → 今天等我来》与这些关系同时成立。作者另行确认的《倒带人生 → 不来也不去》也保留，不能为了加入回环而删掉原有分支。上图经过《浮夸》的部分是本次扩展；原版《任我行 → 孤独患者》已退休。

### 2.3 历史事实和当下创作都要留档

《贝多芬与我》和《Baby Song》先作为待确认歌名，随后得到作者明确回复「确认是对的」。人工确认与此前的查证依据分别保存在 `identity.review` 和 `identity.evidence_type` 中。

后续维护遵守同样的区分：

- 历史前驱记录保留在 `source.predecessors`；当前游戏只读取 `next`。
- 作者新增或替换的关系写入节点的 `route_audit`，包括 `confirmed_additions` 与 `retired_routes`。
- 语义候选保留为候选，不能因图画得通、测试通过或作者确认了另一条路而自动启用。
- 早期 QA 中的「26 节点 / 31 路径」「绵绵后续暂空」「红玫瑰尚为候选」属于当时状态；后来的作者扩展已改变当前版本。

详细字段与确认方法见[数据约定](MUSIC_RIDDLE_DATA.md)。

## 3. 游戏结构：分岔、回环、停驻与抵达

起点是《不来也不去》，主终点是《贝多芬与我》。起点有多个方向；路径可以汇合，也可以回到已经去过的歌。地图上的序号不应暗示线性关卡或唯一正确顺序。

| 状态 | 含义 | 玩家接下来可以做什么 |
| --- | --- | --- |
| 普通节点 | 当前文字可能指向一首或多首歌 | 猜歌、看提示、主动揭晓、沿已知出路继续、回访。 |
| 回环 | 从一条真实路径回到起点 | 保留所有发现与已走路径，继续探索其他分支。 |
| 死胡同 | 一首可以发现、收藏、重访，但没有后续谜面的歌 | 阅读引用、听和弦，退回上一首或选择其他已发现的歌。 |
| 主终点 | 已完成一条抵达路线 | 感受抵达反馈，继续寻找遗漏节点。 |
| 隐藏尾声 | 所有常规节点都已发现后自动出现 | 在终点旁进入额外的致意；不是新的普通答题关卡。 |

本文归纳的体验原则是：**死胡同也应是值得抵达的地方。** 它是支线的停驻，不应用错误答题的视觉或声音对待。抵达终点也不应清空地图、锁住探索或强制重新开始。

必须分开三种状态：当前在哪首歌、找到了哪些歌、沿哪些有向边走过。找到某首歌，不代表从当前歌到它的这条路已经走通。直接在收藏或完整地图中回访，不应冒充解开了新路径。

计数只描述当前出边，例如「下一步 3 条 · 已走通 1 条」或「下一步 1 条 · 已全部走通」。来路用另一种颜色与图例表达，避免重现「有一条连线，但文案说没有未走路径」的歧义。

本文中的主题解释帮助维护者理解取舍，实际谜面和引文请读取 JSON，不另维护第二份文案。新路径不能只接边而不复核当前谜面的指向，尤其是多出口节点。

当前有 3 个独立死胡同：《绵绵》《明年今日》《天下无双》。全收集条件包含它们，但不要求走完全部 47 条边；隐藏尾声没有普通入边和出边，也不提前出现在揭晓列表或未解锁地图中。

## 5. 美术世界：钢琴中心的不可能空间

### 5.1 主体与构图

作者对美术的要求经过多轮具体收敛：音乐主体应一眼可辨；参考演唱会《FEAR and DREAMS》的暗色空间、鲜艳花卉和梦境感；需要具有分叉、回环和不可能透视的**完整埃舍尔式空间**，中央主体是钢琴，建筑路径可以由黑白琴键构成。

最终收敛的构图原则是：

- 黑色钢琴及生长其间的花朵是焦点，键盘、琴身与琴脚清晰可辨。
- 前景、中景、背景建立空间深度，多方向路径暗示分叉、汇合与返回。
- 黑白琴键兼具音乐识别和行走路径的功能；不是随意贴在建筑上的装饰。
- 使用几条较长、舒展的路径和大块留白，减少短阶梯、零碎平台与急折线。
- 色彩集中在中央花朵，周围建筑较暗、较安静，避免细节压过主体。
- 作者要求密集实验减少约三分之一，这是对当时版本的修订幅度；以后应判断主次和留白，不把「三分之一」当作固定算法。

当前主视觉为 `endless-echoes-garden-v5.webp`：

![当前钢琴与琴键空间主视觉](../gallery/music/assets/endless-echoes-garden-v5.webp)

### 5.2 色彩与材质

作者明确不喜欢「脏脏的暗绿色」，并最终要求此页固定深色。当前方向是炭黑、深蓝灰的空间，暖白琴键与文字，朱红、橙色和钴蓝花朵，以及克制的暖色光。2026-10-03 的改版把这条收得更紧：只有花朵和玩家走过的那条金色线索带颜色，界面其余保持炭黑，颜色属于花朵。

当前界面参考色：地图背景 `#161923`、面板 `#21202a`、主要文字 `#f0e8e3`、交互强调 `#f1b291`、来路蓝色 `#91b5ed`。这些是实现快照；后续调整要保持层级、可读性与花朵反差，不必永久冻结每个色值。

页面在首帧就进入固定深色，并省略主题切换。其他页面仍保留全站主题偏好，访问回响不应改写它们的主题。

### 5.3 主视觉与 UI 使用同一组花

作者希望地图节点也是花，并明确要求通过生成素材做出封面中的花。当前使用四张透明生成花朵素材，地图、当前节点、邻接节点和已找到列表共用：

| 数据值 | 视觉特征 | 本次归纳的选择倾向 |
| --- | --- | --- |
| `poppy` | 朱红的薄瓣、深色花心 | 热烈、袒露、缺憾、生命力。 |
| `blue` | 冷蓝色簇花 | 记忆、距离、孤独、时间和克制。 |
| `ivory` | 乳白花瓣与暖黄花心 | 陪伴、庇护、日常、承诺和抵达。 |
| `dahlia` | 橙色、多层放射花瓣 | 暖意、远行、时间轮转和繁盛。 |

这些选择依据形状、颜色、歌曲意象和情绪，不声明固定植物花语。四种花重复出现，构成一致的视觉词汇；并非每首歌都对应独一无二的植物。《红玫瑰》当前也使用朱红罂粟形素材，依据是热烈与缺憾的对照，而非植物名称的字面对应。

后续新增素材要匹配现有花的质感、光线、轮廓与小尺寸辨识度。检查透明边缘、花瓣完整性和自然留白；生成图不能只在大图预览中好看，还要在约 22–56 px 的实际 UI 中可辨。

### 5.4 封面是独立排版

封面标题曾被轮盘卡片裁断，因此以后必须分别设计横版与竖版。当前横版为 `960×600`，竖版为 `600×800`；同一主视觉重排，不能把横图简单居中裁成竖图。

标题保持为可编辑的 SVG 文字，与生成的画面分离。实际验收同时覆盖首页精选、Work 轮盘、分类卡片和页面页首：标题安全区、琴身与花朵完整、底部按钮是否遮字、窄屏缩略图是否仍能认出主体。

### 5.5 线索的字体

线索和标题使用衬线字体（`--echo-voice`，没有衬线字体时回退到界面字体）：线索是谜题本身，花朵是它的情绪，不该只有界面字号。当前线索 17 px、标题 36 px、花朵 84 px。测试用的 OPPO 手机上没有中文衬线字体，中文线索回退成无衬线字体；要统一需要网页字体，这一版没有做。

## 6. 网络版面：像花，也必须读得清

作者要求起点和终点拉开距离、分处对角线，并突出大小与颜色；后来提出整体点线可以像玫瑰。当前地图将起点置于左下，主终点置于右上，尾声在终点旁，以弯曲花瓣与下方支路构成抽象花形。

**玫瑰是整体构图的意向，路径方向和局部辨识是先决条件。** 不为了描摹一朵花而增加不存在的边、掩盖实际分支，或让线路绕出难以跟随的急弯。

维护地图时优先处理：

1. 节点之间留出文字与点击空间；节点和歌名同属可点击区域。
2. 箭头在到达节点前留下可见间隔，避免被花瓣覆盖；多条汇入线的箭头分开。
3. 边避开无关节点；避免长距离贴近、近乎平行的线，以及短边回钩。
4. 走过的路是金色细线，带一层柔和的底光；当前出路是桃色虚线，来路是蓝色；尚未走的整张网络退成低对比的幽灵线，刻意低于 3:1，让它提供方向感而不抢走玩家自己的路。每种状态用各自的箭头。具体数值见设计评审（私有笔记仓库 `qa/2026-10-03-echoes-design-review.md`）。
5. 交叉处用背景色留出分隔，当前相关路径置于其他边之上，节点与标签位于全部边之上。
6. 在完全解锁状态检查所有标签，不能只检查起点附近的稀疏图。

当前 47 条路径均有独立的 `map.routes` 中间点，生成器输出连续曲线；节点位置与连线几何不应改变实际 `next`。画布为 `1620×1240`，只是一版布局参数。

未发现的歌是花蕾（一个点加一圈虚线），不标序号，因为序号会暗示线性关卡；`n / 36` 的进度保留。每首找到的歌在自己的花色里泛起柔和的光晕（叠加混合），一盏灯笼跟着当前歌走，终点有一束缓慢的信标，只脉动三次就静止。光晕随点亮的歌增多分四档减弱，让全部点亮时的地图仍然干净。当前节点、已发现节点、起终点应有清楚区别；颜色之外仍需要箭头、图例（「走过的路」「当前出路」等）、文字、焦点和进度来表达状态。

## 7. 桌面与移动端使用不同的信息重心

### 7.1 桌面：线索与全局同时存在

桌面采用左侧线索、右侧网络的双栏布局。当前歌、花朵、谜面、输入和帮助形成一组，网络让玩家看到走过的路、分岔和汇合。下方收藏提供再次进入已找到歌曲的入口。

避免把线索压成过窄的侧栏，也避免大标题、说明和装饰占满第一屏。视觉改善必须覆盖主谜题面板和所有操作控件，不能只换页首图片。

2026-10-03 的改版让游戏紧接在页首图之后出现：原来那条只重复页面标题、只放一个声音按钮的工具栏被取消，声音控制并入线索栏的顶行（手机上是 44×44 的图标）。确认按钮在输入框为空时是淡底按钮，输入后才变成实心；强色属于花朵，按钮不该比花朵更抢眼。

游戏卡片约 914 px 高，比常见笔记本浏览器的可视高度更高，所以地图栏顶行有「全屏」（2026-10-04，作者提出）：卡片铺满屏幕，地图在线索栏旁剩下的空间里等比缩放，线索栏内容放不下时在栏内滚动。支持全屏接口的浏览器同时隐藏浏览器界面；不支持时卡片盖住整页。真全屏里 Esc 归浏览器，先退出全屏；终章要再按一次 Esc 或点「停止」。手机不显示这个按钮。数字见私有笔记仓库 `qa/2026-10-04-echoes-fullscreen-and-decoys.md`。

### 7.2 移动端：先聚焦单点，再展开完整网络

作者最终提出：「让移动端的视觉重点在单点上，在需要的时候才拉回完整网络。」这是当前移动体验的核心，已经替代「默认显示密集全图，再去底部弹层答题」的中间方案。

当前窄屏默认呈现：

```text
当前歌 / 退一步 / 完整地图
          ↓
已走来路 ← 当前花朵 → 当前出路
          ↓
谜面或引用 → 输入与确认 → 提示 / 揭晓
```

中央花朵是视觉焦点，也可以点击回放和弦。来路只列已经走过的入边；出路列当前真实邻居，未发现时只显示问号与「未接上」，不提前暴露歌名、花色或可访问名称中的答案。

「完整地图」按需打开总览，先显示完整范围，可再放大、平移或定位当前。选择已发现的歌后回到它的线索；关闭和 Escape 返回合适的键盘焦点。

滚动和焦点是本次明确修正过的问题：

- 点按节点、退一步及打开/关闭总览应保留页面位置，避免页面向上跳。答对一题是唯一的例外：触屏上页面在约 0.5 秒后缓缓滑到新线索，标题停在固定栏下方一小段距离；玩家一触碰或滚轮转动就立刻停下，标题已在上半屏时不滑，减弱动态效果时直接跳到位。桌面上页面不动。
- 浏览器自动聚焦也可能造成滚动，因此用不滚动的焦点恢复，并处理面板高度变化。
- 答对之后，桌面端焦点留在输入框，新线索通过安静的 live region 播报，连续答题不会吞掉头几个按键；触屏端焦点移到标题，让屏幕键盘收起。
- 输入框带 `enterkeyhint="go"`、`autocapitalize="off"` 和 `spellcheck="false"`：键盘不自动大写、不拼写检查歌名，动作键直接提交。
- 「放大」「定位」是明确的地图操作；普通点按不应暗中重新居中整页。
- 从下方收藏主动选择一首歌，可以明确回到线索区域；这与在当前面板中保持位置的点按不同。
- 手机输入框与确认按钮各占一行，保留明确间距和足够点击面积。
- 删除冗余「开始探索」按钮，压缩手机页首留白，让线索更快进入视野。

当前聚焦布局断点是 `≤900 px`，平板也采用此模式。断点可随内容复核，桌面与窄屏的任务分工应保留。调整窗口时须正确关闭总览、归还地图并释放滚动锁。

## 8. 声音：每首歌的情绪和弦

### 8.1 选择依据

作者明确选择按歌曲**意象与情绪**设计花朵和声音，又要求把单音改为具有色彩的和弦。随后澄清为**同时发声**。因此每个节点是 3–6 个音（以 4–5 个音为主）组成的同一时刻起音的钢琴和弦；点击一首歌时不能做成逐音弹奏的琶音。路径回放和终章里，和弦可以按编排极轻微地由低到高摊开，那是乐句的表情，不是点击反馈（见 8.4）。

每个节点都有 `presentation.flower_reason` 和 `presentation.chord.reason`，配置不随数组序号变化。音乐设计是界面的独立创作，不是原曲调性、旋律或伴奏的转录。

可延续的和声思路是：开放的悬置表达尚未回答的问题，小和弦与延伸音容纳回忆和距离，暖色大和弦回应陪伴与庇护，属七和弦提供张力或抵达前的推进。它们是设计语言，不是所有歌曲必须套用的情绪公式。

几个关键呼应：

| 节点或路径 | 当前选择 | 设计意图 |
| --- | --- | --- |
| 不来也不去 / 倒带人生 | 相同的 `Csus2` | 让入口与回环听起来相认，悬念仍然开放。 |
| 完 → 贝多芬与我 | `G7 → C` | 以张力到稳定的关系形成抵达感。 |
| 隐藏尾声 | 高音区 `Cmaj7#11` | 在结束之后，以更轻、更高的色彩回应终点。 |

其余节点的和弦、配器和理由只保存在 JSON 中，这里不重抄。2026-10-03 的重配以相邻歌曲之间的声部移动尽量平滑、避免连续重复同一种色彩为准则（37 个和弦有 35 种写法）；入口的 `Csus2`、《倒带人生》对它的重现和《完》接终点的 `G7 → C` 是不动的固定点，尾声的和弦名可以变，但仍应在更高音区回应终点。

### 8.2 音色与操作

作者指定使用 Vocal Coach 项目已有的 YDP 钢琴采样。当前使用同源的 7 个根音 MP3，保留[采样署名](../gallery/music/assets/piano/ATTRIBUTION.txt)。音色统一，回放包括地图节点、当前花朵和已找到列表；重复点按同一个节点也应回应。

每组音符共享音频时钟起点，按音符数量调整增益。当前和弦尾音约 1.4 秒；连续点击会让上一组淡出，避免多组和声叠成杂音。静音、重置、页面隐藏和较新的点击会取消待播放的旧请求。

音效开关与探索进度分开保存。刷新不自动发声；开启音效后由用户动作启动输出。错误、死胡同和终点的意义首先靠界面表达，声音不是完成操作的必要条件。

线索栏里有一排 C3–C5 的和弦键盘（取自页首主视觉里那段琴键阶梯）：当前歌的和弦以这首歌的花色点亮琴键并随声音敲下，其他已找到的歌用过的琴键带一圈很细的暖边。键盘只读取 JSON 里写好的和弦，不从数组序号推导任何东西；要移除它，删掉生成器里的 `keyboard_html()` 和脚本里的 `renderKeys` 调用。

### 8.3 响应一致性属于音乐体验

作者发现点按时播放有时快、有时慢。旧按需机制会在第一次使用某个采样时临时下载和解码，造成探索节奏波动，后续已改为提前准备。

当前在音效开启、页面可见时，使用离线音频上下文预载并解码全部 7 个采样；输出上下文仍由用户操作创建/恢复。缓存就绪后，和弦在地图重绘前直接调度。关闭音效时不预载，失败只重试缺失采样；不支持离线解码的浏览器保留交互时加载的后备路径。

后续优化应继续检查冷启动、缓存、快速切换、静音和失败重试。不能为了「快一点」先播放半个和弦，也不能把旧节点的迟到音效补播出来。浏览器调度时间与扬声器实际发声延迟是不同指标。

### 8.4 路径回放与终章

作者在 2026-10-03 提出：把从起点走到当前歌的路径奏成一段和弦乐句，并调整和弦顺序让它听起来像音乐；集齐所有歌之后自动奏响一首编排好的和弦曲，节点随它亮起又暗下；和弦也要比之前更丰富。作者在 2026-10-04 试听后认为好；这是整体印象，没有逐段记录。

取舍如下，参数和数据格式见[数据约定](MUSIC_RIDDLE_DATA.md#路径回放与终章2026-10-03)：

- **只用已有的和弦。** 乐句和终章都读取节点上的和弦，不引入新的音频文件，也不另写一份「配乐」。要改终章，改 JSON 顶层的 `finale`；要改某首歌的声音，改它的 `chord`。
- **路径是玩家实际走来的那条**：从当前歌曲往回，每首歌取最近一次走进它的边（2026-10-04 作者报告：先由《喜帖街》、再经《花花世界》到《贝多芬与我》，回放的却是《喜帖街》那条）。不是点击顺序，也不使用没走过的边；站在起点（路径只有一首歌）时不提供；到隐藏尾声时沿终点接上。
- **终章是奖励，不是关卡。** 集齐后约 2.9 秒（让最后一个和弦和点亮动画先结束）自动开始，之后可在地图上方重听或停止；重新载入已集齐的存档不会自动播放。
- **声音关闭时不越俎代庖。** 回放和终章的按钮此时禁用并说明原因，不覆盖玩家的静音。
- **随时可以打断。** 点击歌曲、答对、Esc、静音、重置、切走页面都会终止；答错不会。手机上终章在完整地图弹层里播放，关闭弹层即停止。
- **终章期间请求屏幕常亮**，免得手机自动锁屏在乐句中途切断声音；结束或停止时放开，浏览器不支持或拒绝时终章照常播放，路径回放不请求。
- **和声以连贯为准。** 见 8.1：相邻歌曲的声部移动尽量平滑，入口、回环和终点的呼应不动。

代码上，时间、力度和路径逻辑是 `src/ts/echo-score.ts` 里的纯函数（Node 可测），排队、动态和取消在 `EchoPiano.Player.playScore`。

## 9. 动效：表达发生了什么

作者要求节点点亮有光效，回到起点与到达终点有特别反馈。动画因此要依附真实的探索事件：

| 事件 | 反馈方向 |
| --- | --- |
| 发现新歌 | 节点显现、短暂的花朵/光环变化，刚走过的真实路径有光掠过。 |
| 沿路径回到起点 | 起点的返回光效，文字说明回到最初而已走路径仍在；共享入口和弦。 |
| 沿路径抵达终点 | 更明确但短暂的抵达光效；玩家仍能立即操作和继续探索。 |
| 全收集 | 隐藏尾声出现，提供明确通知和入口；约 2.9 秒后终章自动开始（见 8.4）。 |
| 回访已发现节点 | 切换当前状态、回放和弦；不伪装成再次发现或新的终点抵达。 |
| 答对（新发现） | 输入框下的提示条显示找到的花、歌名和计数（回访不显示计数）；线索花朵绽放并响起和弦，地图节点同步泛起光环，新歌的颜色轻染线索栏。 |
| 答错 | 输入框轻微横移（减弱动态效果时不晃动）并记一次；同一首连续两次答错后，提示图标闪三下。 |
| 差一点（诱饵） | 输入的是该节点 `decoys` 里的歌（如孪生歌《白玫瑰》对《红玫瑰》）：用普通强调色显示这首歌自己的一句话，例如「很近了：……它是粤语版。试试国语那首。」不晃、不记错、不标红。 |
| 回响这条路 | 路径上每首歌一颗花珠，随和弦依次点亮，并显示正在发声的歌名；地图上有一束光沿路径前进。 |
| 终章 | 地图变暗，节点随各自的和弦亮起、再随衰减暗下，聚光灯和键盘跟着走；沿图的边相邻的两步还会点亮那条路。 |

光效用于强调一段路径和一个节点，避免全图持续闪烁、光晕吞掉箭头、动画抢走输入焦点。遵从 `prefers-reduced-motion`，关闭动画后仍保留文字、状态和操作反馈。

## 10. 文案与引用的分工

作者明确要求说明文案强调「扩展版」，并且不要提具体歌名；这适用于页首和下方介绍等**公开解释性文案**。实际发现后的节点标题、谜面和本设计文档仍需要歌曲名称。

介绍应回答三件事：旧作如何被复原、现在加入了哪些类型的探索、怎样玩及怎样保存。不要提前列出终点、隐藏尾声歌名或完整路线。

花朵是美术语言，不能把「确认答案」「已找到」「揭晓」改成「开花」等隐喻操作。当前直接文案可延续为：

- 「读一段线索，猜下一首歌。」
- 「下一首是什么？」「确认答案」
- 「给我一点提示」「揭晓答案」
- 「退一步」「完整地图」「定位当前」

提示和揭晓分开。提示帮助联想，揭晓由玩家主动打开，并明确告诉玩家选择答案后会沿这条路继续；当前两者互斥展开。不能用隐约的图标或过小点击区域承担这些关键操作。

### 引用与普通谜面

作者要求凡引用歌词的文案使用大字号 quote 样式。判断依据是文字来源，而不是它是否短、长、诗意或像歌词。

- 整段谜面属于引用时用 `clue_format: "quote"`，文字仍只维护在 `clue.zh/en`；页面输出 `blockquote`，不重复展示普通正文。
- 独立引文用 `quote`，与解释性 `clue` 分开；《绵绵》属于这一种。
- 作者给定的意象文案、改写和解释用普通正文；不能只因用了引号提交，就擅自宣称它是已核实的原歌词。
- 引用保留作者指定的措辞与标点。若发现与发行歌词有差异，另行记录核验和修正决定，不在排版改动中悄悄替换。

当前明确采用引用样式的节点是《绵绵》《明年今日》《今日》《天下无双》。《今日》的谜面原先是作者给定的措辞，与发行歌词有差异；作者在内容评审后确认改用发行歌词「像处圈中圈」。《绵绵》的引文同样按歌词资料把「下雨天」改为「夏雨天」（2026-10-04，作者授权按查证结果改）。未来若确认其他节点也属于直接引文，同样采用引用样式。

当前中文引用字号约桌面 22 px、手机 21 px，按语句分行；英文译文自然换行。字号、换行和引用标识应跨节点一致，长段也不能截断。

## 11. 数据与扩展工作流

歌曲数据统一使用 JSON，不同时维护 YAML、歌名表或第二份可编辑路径表。设计意图也要进入数据：花朵与和弦各有选择理由，身份与路径各有证据和确认记录。

| 数据层 | 权威位置 | 维护要点 |
| --- | --- | --- |
| 歌名、别名、谜面、提示、当前出路 | `data/music-riddle.json` 的节点字段 | `next` 是当前真实图；改标题保留 `id`。 |
| 历史证据与人工决定 | `source`、`identity`、`route_audit` | 原始记录与当前扩展并存，候选与确认分开。 |
| 花朵与和声 | `presentation` | 明确选择与理由；`midi` 是实际配器，和弦名称只是说明。 |
| 终章编排 | 顶层 `finale` | 每一步指向一个节点，给出拍数、力度、摊开时间和衰减；时间与路径逻辑在 `echo-score.ts`。 |
| 地图几何 | `position`、`map.routes` | 布局调整不能隐式修改游戏连接。 |
| 作品入口和分类 | `data/site.json` | Games、首页创造、封面与历史 URL 保持对应。 |
| 页面说明与结构 | `scripts/build_music_riddle.py` | 修改生成器，再生成 HTML 与封面。 |

新增一个节点时，依次完成：

1. 判断属于存档复原、作者扩展还是尚未确认的候选，记录依据。
2. 建立唯一稳定 ID，填写标题、明确的简繁体等别名、双语谜面与提示。
3. 指定入路与出路，检查上下游谜面是否仍表达全部出口；终端节点明确标记。
4. 为花朵、和弦及配器写出具体理由，不按序号取模随机分配。
5. 放入完整地图，检查节点、标签、箭头、交叉和聚焦邻域；新增更多邻居时复核手机可用空间。
6. 验证答案、分支计数、旧进度迁移与隐藏尾声条件。
7. 生成页面，进行实际渲染和交互 QA；获准发布时再通过 GitHub Actions 完成发布和线上回验。

只有答案、没有后续谜面时，可先用 `open_answers` 明确留空。作者给出完整设计后再升级为节点；移除同名占位，避免答案同时走两套判断。独立死胡同使用 `terminal: "dead-end"` 与空 `next`，不要编造后续谜面。

当前和弦约定是 3–6 个互不重复、按低到高排列的 MIDI 音高，范围 `48–72`（C3–C5，C4=60）。改和弦名称不会自动改变音符。

旧进度按稳定 ID 迁移：保留已找到的现存歌曲，过滤删除或退休的边，不自动把新歌计为已发现。隐藏尾声每次按当前全部常规节点重新计算解锁；扩展增加歌曲后，不能继续沿用旧版全收集资格。

新谜题可从[最小模板](templates/music-riddle.json)开始，但页面介绍、封面、作品入口和地址仍需单独设计。可复用的是数据约定和探索机制，不必把回响的钢琴、花朵或具体歌曲结构原样套给所有作品。

## 12. QA 与发布的验收指引

本次最重要的 QA 教训是：**没有横向溢出，不等于视觉已经验收；试玩通过，不等于歌曲身份或谜底完整性已经证实。**

每次变化按相应层次检查：

| 层次 | 需要的证据 |
| --- | --- |
| 内容与来源 | 歌曲身份、前驱方向、作者新增/退休记录，谜面是否覆盖当前出口。 |
| 游戏状态 | 每条新路径、未知/已知节点、走边计数、死胡同、终点、全收集、刷新恢复。 |
| 视觉 | 实际封面容器与完整图，长标题/引用，中英文，窄屏、短屏、平板与桌面。 |
| 操作 | 指针、键盘、提示/揭晓、回放、地图开关、滚动和焦点、减弱动态效果。 |
| 声音 | 首次准备、同时起音、重复回放、连续切换、静音、失败重试与取消；路径乐句和终章的排队、打断、总线不爆音（离线渲染的峰值与削波）、屏幕常亮的请求与释放。 |
| 发布 | 本地检查、GitHub Actions 的检查与部署、线上资源与实际行为分别核对。 |

视觉测试至少覆盖约 320 / 390 px 窄屏、平板和桌面，并加短屏情境。实际页面视口要核实；截图捕获曾出现旧画布或额外空白，不能为了补偿工具伪影而改产品 CSS。自动点击工具也可能先滚动元素，判断页面跳动需实际指针坐标或其他可靠证据。

重点回归组合包括：完全未解锁与完全解锁的地图、三出口节点、最长引用、隐藏尾声出现前后，以及正在打开总览时改变窗口尺寸。测试进度应备份，避免覆盖作者正在玩的收藏。

页面资源应控制加载与布局变化：主视觉保留固有尺寸，小花素材复用，浏览器所需数据不携带无关历史证据；音效关闭时跳过采样预载。性能指标注明环境与测量方式，不能把一次实验室 CLS 或调度延迟说成真实用户的体验承诺。

当前自动与浏览器证据见对应 QA 文档（2026-10-08 起在私有笔记仓库的 `qa/` 下，不再公开）；数字（测试数量、耗时、测得的像素）只写在那里，本指引不抄，以 `make check-all` 的实际输出为准。这些证据只属于当时的版本，不替代今后改动后的检查。

改版时在一台 Android 手机（OPPO Find X8 Ultra，Chrome）上做过真机验证，见设计评审（私有笔记仓库 `qa/2026-10-03-echoes-design-review.md`）。真实 iPhone / Safari 的触摸、软键盘、音频恢复和输出延迟尚未验证；屏幕常亮只对着替身接口测过，没有在任何真机的自动锁屏下试过。不同扬声器上的主观和声色彩、总体玫瑰构图的审美验收也不由结构测试代替；音频批次作者已于 2026-10-04 试听，认为好，没有逐段记录。

## 14. 下一轮设计的判断顺序

以下是本文根据现状提出的维护建议，不是本会话新增的实施授权：

1. 先补齐 iPhone / Safari 的真机验收，尤其是键盘打开、总览进出、快速回访、浏览器重新恢复音频，以及终章能否在最后一次答题的手势之后自动开始、屏幕常亮是否生效。
2. 和弦与终章编排已由作者试听认可；今后改和弦或编排后仍要重新试听，音量、音区、色彩和连续导航时的衔接以耳朵为准，保留已有理由，但允许作者据听感调整。
3. 若再扩展节点，先检查当前 36 节点版的邻域容量、全图标签与曲线路径，再判断是否需要新的布局层次。
4. 继续统一封面、花朵、网络与 UI 的质感；新增素材需要明确改善辨识或意象，不因「还能更繁复」而堆叠细节。
5. 已知但未处理的小毛病：手机上关闭终章的完整地图弹层后，焦点回到「完整地图」按钮，页面随之从答题处滚到该按钮（实测 769 → 299 px），不会回到刚才输入的位置。

判断任何新方案时，回到五个问题：能否一眼认出音乐主体？能否读清当前线索与路径方向？手机能否留在当前节点完成操作？声音是否及时且具有意义？以后能否从数据和理由中理解、修改这项决定？
